## LAN findings and testable hypotheses

Verified source facts:

- `src/server/emulator/connection.rs::set_emulator_previews` subscribes requested monitors through ordinary `capture_displays`; it does not request a scaled thumbnail stream. Thus monitor previews can process full 2560x1440 frames despite small displayed cards.
- On Android/iOS, `src/flutter.rs::on_rgba` uses the software RGBA delivery path. `flutter/lib/models/model.dart::_decodeDashboard` imports the full raw pixel image through `decodeImageFromPixels`, then the UI presents a `RawImage`. The desktop texture preference is desktop-gated. This path is inherited on mobile, not proof that the redesign accidentally disabled a working Android texture renderer.
- One 2560x1440 4-byte pixel frame contains 14.06 MiB; 30 frames represent about 422 MiB per second of raw pixel data per monitor. This arithmetic describes potential memory handling, not measured copies or network bitrate.
- The native RGBA slot already rejects new publication while Dart owns its pending buffer. There is no evidence here for an unlimited Dart image queue.
- Desktop compressed-video queues have capacity 120; decoder-speed adaptation and refresh already exist. Capacity alone does not establish a real backlog. Dropping arbitrary interframes can break reference-dependent decoding.
- V4 subscriptions normally keep only the selected monitor in fullscreen unless the chooser opens, and pause dashboard previews in background/tools. Adding these behaviors again would duplicate existing work.
- Direct transport and a low RTT do not measure capture-to-presentation or input-to-visible-response delay. Historical screenshots reported low Direct RTT, but this recovery did not reproduce current phone slowness.

Ranked hypotheses to test, not a confirmed diagnosis:

1. **Binary mismatch:** the installed host lacks recent fixes. Prediction: a verified matched host/phone pair changes guest freshness/backlog behavior relative to the old pair.
2. **Full-resolution multi-stream work:** multiple monitor streams stress decode/pixel import/rendering on the phone. Prediction: one monitor with the chooser closed has lower presentation cost than the overview or multi-monitor chooser; reduced source resolution lowers that cost.
3. **Capture/codec/decoder throughput:** host encoding or phone native decode cannot keep pace. Prediction: capture/encode time or compressed queue age grows independently of RTT, and changes with codec/quality at fixed targets.
4. **Routing/transport contention:** a connection labeled Direct still suffers packet/service contention. Prediction: transport or send backlog tracks delayed frames even when decode/presentation are fast; compare verified same-LAN direct routing and transport samples.

Do not apply speculative global queue reductions, force desktop texture settings on Android, or implement Eco Mode as a latency fix before establishing the responsible stage.

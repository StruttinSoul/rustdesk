# MIRPG Remote Capability and Action Contract

This table is the WP1 gate for capability negotiation, ownership, authorization, acknowledgment, timeout, and reconciliation. It is a contract for later work packages, not evidence that later-package operations are implemented.

## Shared operation rules

- `CapabilityStatus` is `supported`, `unsupported`, or `unknown`. If a peer does not negotiate a capability list, new capabilities remain `unknown`. If it negotiates a list but omits a capability, that capability is `unsupported`.
- Consequential requests use a unique `operation_id` plus the authenticated `session_identity`, the exact `target_identity`, and the current `session_generation`. `request_id` remains transport/request correlation and is not an idempotency key.
- Consequential replies distinguish whether the request was accepted from whether it was applied. Implemented WP1 host replies carry `accepted`, `state`, `error_code`, `error`, the same operation/session/target/generation identity, and an observed `snapshot` when one is available.
- `pending` may become `applied`, `failed`, or `unknownOutcome`. A timeout, generation change, or lost acknowledgment never becomes success. The client reconciles current state before offering or issuing a consequential retry.
- A reconnect or authenticated login-scope change advances/rotates operation scope. Pending work from the previous scope becomes `unknownOutcome`; it is never replayed automatically.
- Host authorization is authoritative. Hiding or disabling a Flutter control never grants permission. Payload bounds and target checks are enforced again on the host.
- Old peers keep established read-only/basic behavior where compatible, but every new consequential action stays hidden or disabled until its capability and required acknowledgment contract are negotiated.

## Implemented WP1 wire details

The current host inventory advertises `operation.identity.v1`, `operation.ack.v1`, `host.status`, `host.process_end`, and `host.recover.bluestacks_adb`. Flutter requires both operation contract capabilities plus the specific mutation capability before sending `process_end` or BlueStacks ADB recovery.

`process_end` and `recover` are synchronous host actions: `accepted: true` means the authenticated, authorized request reached the bounded handler; `state: applied` means that handler reported success. A valid accepted request can therefore return `state: failed` with a typed `error_code`. Unsupported handler actions return `accepted: false`. A successful mutation followed by snapshot failure remains `applied` and reports `observation_error_code` rather than being rewritten as a failed mutation.

The current completed-operation replay cache is scoped to the authenticated connection/login generation and bounded to 64 completed host mutations. It prevents immediate/retry re-execution within that scope and permanently binds a retained operation ID to its original action/target. The client does not automatically retry or replay consequential actions. After timeout or generation loss it refreshes/reconciles instead of assuming success.

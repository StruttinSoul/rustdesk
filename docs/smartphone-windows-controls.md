# Windows control from an Android phone

Research and implementation direction, October 2, 2026. Research was performed inline under the user's no-agent instruction. This compares documented controls, not app-store rankings or measured performance.

| Product | Documented mobile interaction | Applicable pattern |
| --- | --- | --- |
| [Chrome Remote Desktop](https://support.google.com/chrome/answer/1649523?co=GENIE.Platform%3DAndroid&hl=en) | Trackpad is the default: swipe to move, tap to click, two-finger scroll, pinch zoom, hold and drag. Windows can use touch modes. | A phone should move a visible pointer without covering the Windows target. |
| [Microsoft Windows App](https://learn.microsoft.com/en-us/windows-app/input-keyboard-mouse-touch-pen) | Android supports direct touch and mouse pointer modes; pointer gestures include click, drag, wheel scrolling and pinch zoom. | Separate local viewport gestures from remote mouse actions. |
| [AnyDesk](https://support.anydesk.com/docs/anydesk-for-android) | Desktop sessions default to mouse mode; touchpad and touch modes are available. Session controls include keyboards, special keys and monitor selection. | Keep input tools and monitor selection reachable from the session. |
| [TeamViewer Classic](https://www.teamviewer.com/en/global/support/knowledge-base/teamviewer-classic/mobile/android/touch-interactions-vs-mouse-interactions-on-android/) | Android phone-to-PC connections use mouse interaction; tablets can offer touch or mouse modes. This source describes Classic specifically. | Choose interaction for the target and device; Android game touch differs from Windows pointer control. |

## Decision for MIRPG Remote

The reported Windows dashboard view fits a high-resolution monitor onto a phone and forwards raw pointer presses, without zoom controls. The resulting targets are too small. Implement a phone-side monitor view with a readable initial zoom, explicit zoom/overview buttons, a visible precision pointer, one-finger trackpad movement, tap/double-tap click, hold to drag, two-finger scroll, pinch zoom and edge-following viewport. Keep a keyboard/text panel and useful Windows keys available in the right rail. The existing live target switcher remains on the left.

Do not change PC resolution, Windows DPI, display drivers or capture transport automatically. Zoom only crops/scales the local image; it cannot add detail that the stream did not transmit. This is a client interaction change, not a latency or image-quality claim. Android/BlueStacks retains direct touch. Existing authentication and view-only restrictions apply to every pointer, scroll and text action. Cancel held mouse input on target changes and backgrounding. Use a fresh viewport for each monitor identity/dimension set rather than coordinating preferences across targets.

Verify readable zoom/overview controls, gesture separation (swipe/pinch cannot start mouse drags), and view-only protection with widget tests. Build a matching test-upgrade APK and inspect on the authorized phone if its debugging endpoint remains available. Cold-boot emulator acceptance remains separate and unverified.

## Delivered local test build

Version 2071 (`1.5.0-test2071`, ARM64) adds these controls. Starting scale targets one native desktop pixel per logical phone pixel, capped at six times the full-monitor overview. The pointer stays visible as the viewport follows it. Fit screen returns to the full monitor. Keyboard text is composed locally and sent with Send; special keys are available separately.

Verification: all 161 Flutter tests passed, including three focused monitor-control tests. Analysis of the widget, dashboard and new tests reported no issues. The optimized Android build succeeded. APK integrity and signature verification passed; its signing certificate matches version 2070. RustDesk native code, the Flutter engine and C++ runtime are byte-identical to version 2070; the compiled Flutter application changed. The source archive contains 1,006 files with verified per-file hashes. Temporary build properties were restored.

Phone deployment: the authorized Samsung phone connected at its updated wireless debugging endpoint. Installing the APK as an upgrade succeeded; Android reports version code 2071 and version name `1.5.0-test2071`. Starting its MainActivity succeeded. The phone's keyguard is showing, so real-device gesture/rendering verification remains pending user unlock. No public release or Windows service changes were made for this update.

Regression surface: the existing `flutter/lib/mobile/pages/target_dashboard_page.dart` fullscreen monitor display/input path now uses the new feature-specific widget, maps its desktop coordinates into the selected monitor, and exposes the keyboard panel. Its permission/background callbacks release held monitor input. These changes are necessary for readable zoom and trackpad gestures. Dashboard cards, target switching, BlueStacks direct touch, authentication, capture transport and host behavior were not changed by this update.

## Keyboard correction: test 2072

The phone reproduced the reported Windows failure: tapping the focused monitor text field left Android's `mInputShown` false. Its activity still had `FLAG_ALT_FOCUSABLE_IM` set by the existing RustDesk remote-session code. The monitor keyboard action now awaits the existing `enable_soft_keyboard` operation before opening the sheet, checks that the selected monitor still permits input, and restores the session keyboard behavior in `finally` when the sheet closes. This correction only changes `_monitorKeyboard` in `target_dashboard_page.dart`.

All 161 Flutter tests passed and the three analyzed files reported no issues. The native window flag cannot be reproduced by those Flutter widget tests; the real-phone check above is the red-capable reproduction. Test 2072 built successfully, passed APK integrity/signature checks, matches the previous signing certificate, and was installed successfully. Android reports `1.5.0-test2072`. RustDesk native code, the Flutter engine and the C++ runtime are unchanged from 2071. The matching source archive was verified. Post-fix Windows keyboard/typing validation awaits the phone being unlocked and left in the Windows monitor view; its last observed screen was the phone lock screen.

The emulator report had a separate configuration cause. Both installed Android 13 BlueStacks instances (`Tiramisu64`, `Tiramisu64_2`) had the existing Android Latin keyboard enabled but `show_ime_with_hard_keyboard=0`. The preference was changed to `1` and read back in each instance. Previous values and applied state are saved in `%LOCALAPPDATA%/MIRPG/bluestacks-keyboard-state-2026-10-02.json`. Tapping the existing game text field in the second instance then visibly displayed its Android keyboard, confirmed by a guest screenshot and `mInputShown=true`. No text or credentials were entered. The first instance's preference is verified; its current game sleep screen was preserved. This fixes the currently installed instances; no emulator protocol or binary change was needed. See [BlueStacks' supported on-screen keyboard workflow](https://support.bluestacks.com/hc/en-us/articles/360061968892-How-to-use-a-virtual-on-screen-keyboard-on-BlueStacks-5).

The local test package includes `Restore-BlueStacks-Keyboard.ps1`. It restores only the recorded keyboard preference when the original instance endpoint still matches and the current value still equals our applied value. Its parser check and both instance dry-run checks passed. Restoration itself was not executed. An initial read with bundled BlueStacks ADB unexpectedly restarted the default ADB server because of a version mismatch; the current SDK server was restored and subsequent work used the isolated port 5038. Emulator keyboard preferences and the Windows phone keyboard action are the complete regression surface for this correction.
